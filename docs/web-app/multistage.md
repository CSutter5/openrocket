# Axial multistage rockets

The November 20, 2026 request authorizes creating/editing multistage rockets and running imported multistage `.ork` files in the web app. ADR-35 supersedes the single-stage limits in the earlier drawing, configuration and imported-flight records for this slice. Production simulations still execute in the browser using the pinned Java engine; desktop sources are unchanged.

## Behavior and boundaries

Use the existing Stage palette entry and component tree to build axial stages. Stage zero is the uppermost stage; subsequent stages follow in rocket child order. Enable each body/inner tube’s Motor tab and use Select motor to assign motors to each mount in the selected configuration. Mount labels include the stage number and name in multistage designs. New configuration now writes an active flag for every axial stage and creates the existing linked simulation. Assign additional stage motors through Select motor.

Motors & Configuration → Stage settings edits active flags, stage separation event/delay/altitude and each mount’s ignition event/delay for the selected configuration. The topmost stage has no separation control, matching the desktop saver. Values initially reflect native default inheritance plus archived overrides. Changes create or replace only the selected configuration’s corresponding override; default settings and other configurations remain intact. Measured controls have independent working unit selectors; changing units does not write the archive. Cancel discards the draft. The final active stage cannot be disabled, since desktop reload would reactivate stage zero. Unsupported pods/parallel boosters disable this dialog.

The trusted `staging` command checks the archive hash, configuration, stage UUID, allowed enums, finite decimal values, non-negative delays and mount ancestry. It publishes a private candidate only after archive export/reimport and document description. The same reducer executes in the shared Durable Object with the existing editor authorization and token checks. Physical edits invalidate stored results while preserving their settings, events, series, sidecar identities and attachments.

The flight projection accepts direct axial stages, complete unambiguous configuration stage flags, multiple single-instance mounts, default/per-flight separation and ignition parameters, and the existing supported recovery settings. It retains the 64-component/16-configuration bounds, exact motor-curve/digest checks, explicit field allowlists, and refusal of pods, parallel stages, motor clusters and imported extensions/scripts. Like desktop `MotorHandler`, a compatible catalog digest takes precedence over an embedded curve; embedded-only motors remain supported and all original attachments stay preserved. Older bundled archives contain rounded embedded mass samples, so using them ahead of the catalog changes flight dynamics even when their compatible digest passes. At least one active stage must have a resolved motor. Recovery is optional, allowing native booster tumbling/ground-hit behavior. This is a bounded multistage extension, not general desktop parity.

The bundled examples require additional previously analysis-only component types, freeform fin points and fin tabs. These now use native constructors and setters in flights as well. Freeform input is bounded to 3–64 finite points; tab aliases must agree. Materials use the desktop `Databases.findMaterial` overloads, retaining stock lookup and the distinction between missing and explicit shear modulus. The lookup does not mutate account preferences or register request materials globally. Unrepresented physical fields continue to refuse.

Multistage preview geometry comes from the same reconstructed native rocket, using selected active components and their actual locations. CG/CP, mass and internals share that configuration. Shell profiles and uncanted fin outlines are selectable by UUID; unsupported shapes remain listed. The separate single-stage drawing path retains its existing limits. Results retain legacy primary-branch fields and add all named flight branches with source-UUID events and nullable time/altitude/speed/acceleration samples. Undefined terminal acceleration is serialized as `null` in the primary series too, including native aborted runs, instead of inserting a bare `NaN` into JSON. Native abort events remain in the result. Graphs show each branch with a label and distinct dash pattern as well as color. New results remain session results under the existing provenance/staleness rules.

## Engine adaptations

Freeform native validation reaches `java.awt.geom.Line2D.Double`, absent in TeaVM. The build-time class remapper redirects just that segment API to `PortableLine2D`, using the JDK orientation/projection algorithm including collinear and degenerate cases. The JVM reference continues to use JDK AWT. A second adaptation changes `%g` to `%s` in the exact eager stage-branch logging format string because TeaVM does not implement `%g`. It changes diagnostic formatting only. Neither adaptation changes the desktop source pin or simulation algorithms.

## Acceptance and handoff

`web/app/test/multistage.mjs` runs both bundled two/three-stage examples across all five configurations, compares complete reconstructed rocket/configuration serialization with independent desktop loading, compares native geometry/statistics, and runs saved-settings simulations in real Chromium workers against JVM flights. It checks branch counts and ignition/separation events as independent staging expectations. It also exercises the Stage settings dialog, active-stage changes, configuration isolation, stale/invalid refusals, exact unchanged downloads, palette/mount creation and a newly configured two-stage flight. `MultistageDesktopProof` compares 10,000 segment pairs, including collinear and degenerate segments, against JDK `Line2D`.

Static mass/geometry and reconstructed component/motor inputs use 1e-10 SI-unit bounds. Scheduled launch/ignition/burnout/ejection/separation events must match by type, source UUID, order and time (1e-10 s). The standard saved-flight bounds remain 1 ms time, 0.12 m altitude, 0.25 m/s speed and 3 m/s² acceleration, with summary limits of 1 mm altitude, 1e-6 m/s speed and 1 ms times. A detached booster can gain a 1 ms apogee event step from roundoff. Unequal adaptive grids are compared in both directions by interpolation at common times, checking endpoints/events separately; row-count equality is not a physics requirement.

Two explicitly identified three-stage corpus cases need their own numerical limits. Configuration `05896b5a-71a7-48ac-b7ae-eadeb267975b` allows 1 cm maximum altitude and 0.01 m/s maximum speed differences (also used for its RK6 check and the newly created C6 two-stage fixture) while retaining the standard series/time bounds. Configuration `b13e8ca2-f54d-4ca8-9b23-06c6c9eb237a` allows 0.1 m maximum altitude, 0.25 m/s maximum speed and one requested 0.05 s step for apogee/landing times; common-time series bounds are 0.12 m altitude, 0.5 m/s speed and 20 m/s² acceleration. This long C6 flight has different adaptive samples near its sharp thrust tail; sample maxima and the step reporting apogee can differ despite equivalent inputs. Acceleration is especially sensitive to interpolation of that tail. These explicit corpus bounds are stricter than a one-step propagation at roughly 130 m/s and are not universal accuracy claims. ## Rail-button preset import follow-up

The user's `example 2stage.ork` reproduced both a blank preview and disabled simulation. The reconstruction refused `railbutton/preset`, then the drawing fallback misleadingly reported a single-stage limit. The file contains two axial stages, 25 components and six saved configurations. Its personal rail-button preset is absent from the pinned database, but the archive explicitly records the physical dimensions, material, finish and mass override.

ADR-36 adds a bounded saved-state projection for rail buttons. A reference must have the supported type, nonempty manufacturer/part number and a 32-digit hexadecimal digest. Complete geometry, material, finish and mass override fields must follow it, matching native saver ordering. Any explicit drag override must also follow it. Existing scalar, duplicate-field and native setter validation remains active. The model consumes those scalar fields while the archive retains its exact preset reference. This supports serialized rail-button state without adding personal catalog lookup or extending other preset policies. Unsupported multistage drawings now show the actual reconstruction reason.

`web/app/test/rail-button-preset.mjs` is part of application acceptance. It generates an independent two-stage fixture from the bundled example, registers a real desktop rail-button preset with geometry, material, finish, screw/nut mass and positive drag coefficient, and saves subsequent physical overrides. The native oracle proves that it loaded that preset, verifies the explicit mass/drag/dimension overrides, and compares complete reconstructed rocket state, preview statistics, exterior/internal geometry and both flight branches. Only appearance and unordered keyed recovery-configuration serialization are normalized. No physical values are normalized. Negative cases cover missing geometry/mass, wrong preset type and a reference after its scalar state; each refuses simulation, explains the drawing failure and retains an exact download. The user's archive remains an optional local argument and is not committed.

The production application build (`npm run build:app --prefix web`) and `node --experimental-strip-types web/app/test/rail-button-preset.mjs 'example 2stage.ork'` passed with the documented desktop classpath, Chromium 149.0.7827.55 and a Vite production preview at port 4180. The latter checks the owned fixture and all six user configurations against independently loaded desktop state and saved simulation settings, including warnings and source-identified events. It uses the standard 1 ms / 0.12 m / 0.25 m/s / 3 m/s² series bounds and 1 mm / 1e-6 m/s / 1 ms summary bounds without new exceptions. The largest observed series differences across these seven cases were approximately 1.56e-6 s, 9.93e-5 m, 2.77e-5 m/s and 2.61e-4 m/s²; maximum apogee-summary difference was approximately 1.07e-5 m. Preview values and geometry passed at 1e-10. Downloads were byte-identical. The resulting user-file preview screenshot was visually inspected. The existing `node --experimental-strip-types web/app/test/multistage.mjs` also passed all bundled configurations, native branch comparisons, RK6, stage settings, creation and segment geometry checks. `git diff --check` passed. The full application acceptance suite and coediting suite were not rerun for this follow-up.
