# Rocket names and account passwords

The November 20, 2026 follow-up authorizes renaming owned rockets and changing account passwords. Owners and the protected administrator receive Rename rocket actions in the library and editor header. The native modal supports Cancel/Escape and enforces a nonempty display name of at most 100 characters. Renaming changes D1 directory metadata and the editor header, preserving the shared URL, immutable UUID, archive filename and internal component names. Existing document component-name editing remains independent. Names are rendered as text.

The authenticated same-origin rename endpoint requires the immutable rocket ID and expected old name. A conditional D1 update refuses stale confirmations, concurrent renames, deleted rockets and unavailable owners. Other signed-in editors can still edit public document content but cannot rename another owner's directory entry. Renaming does not rewrite archive bytes or invalidate physics results. Other open pages refresh metadata on reload; this does not add a second collaboration protocol for directory metadata. No schema migration is needed.

Account settings is linked for every fully initialized account at `/?account=settings`, avoiding a new reserved username/path collision. The current password, new password and matching confirmation are required. The pinned Better Auth change-password API verifies the old credential and validates/hashes the replacement. It issues a new current session; D1 revokes other sessions, and the existing administrator bootstrap flag/counter update applies only when that user is the singleton administrator. The old admin-only password endpoint delegates to the same helper for compatibility, while the generic account endpoint cannot grant privileges.

Username sign-in now compares the stored credential hash before and after the library call for every user, replacing the earlier admin-only counter check. The hash is an opaque in-memory revision check, never returned, logged or hashed again by application code. If the credential changed during authentication, the new session is deleted and its cookie is not returned. This extends the existing race protection to ordinary password changes without an additional schema or bespoke cryptography. Existing sessions are rechecked before shared writes and persistence; a write already past the final check may complete. Email recovery and username changes remain outside scope.
