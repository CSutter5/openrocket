# Accounts and public rockets

The November 20, 2026 follow-up authorizes accounts and multiple rockets owned by each account. The user explicitly chose public viewing and editing by every signed-in account; per-rocket sharing permissions remain future work. This supersedes the username-only room and account deferrals for this bounded increment (ADR-27). It does not add account administration, private documents or version history, or pass the broader G1/G2–G7 gates.

## Data and ownership

| Location | Owned data |
| --- | --- |
| Cloudflare D1 (`DB`) | Better Auth users, password accounts and sessions; rocket owner, display name, URL slug and immutable rocket UUID |
| Cloudflare Durable Object per rocket | Latest complete archive, opaque attachments, existing simulation identity sidecar and concurrency token |
| Browser Workers | Derived views, selection, units, chosen flight configuration and newly computed simulation results |

Production uses Cloudflare bindings exclusively. `drizzle-orm/d1` connects Better Auth to D1; the SQLite schema/dialect describes D1's SQL format, not an application-managed SQLite file or local database server. Wrangler emulates the same D1/DO bindings for development and isolated tests. There is no filesystem database driver, external database service, R2 dependency or production JVM.

A real remote D1 database named `openrocket-accounts` was created in the connected Cloudflare account and migrated with `web/app/migrations/0001_accounts_and_rockets.sql` through [Cloudflare D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/). Its binding ID is `89cb86bd-db35-4e83-95e2-1e59df10a751`. A remote read verified `user`, `session`, `account`, `verification` and `rocket` tables, with zero user and rocket rows. No real or test accounts were inserted into that remote database. Unrelated databases were untouched. This task did not deploy or alter the live Worker, upload an auth secret, publish a PR or push Git changes.

Each rocket belongs to the session user who creates it; a client-supplied owner ID cannot assign another owner. The unique `(owner_id, slug)` constraint permits `/alice/alpha/` and `/bob/alpha/`, while refusing duplicate Alice paths. Each immutable rocket UUID selects `rocket:<uuid>` in the existing Durable Object namespace. For empty rockets, metadata creation precedes lazy document initialization: the first visitor materializes a native empty rocket with its chosen name and `<slug>.ork` filename. A failed initialization can retry without changing the metadata or another document.

The home page lists all public rockets. `/alice/` lists Alice's rockets, and `/alice/alpha/` opens that rocket directly; missing trailing slashes redirect to the canonical path. URL usernames normalize to lowercase and use 3–32 letters/digits/hyphens/underscores, starting with a letter, excluding reserved application names. Slugs use lowercase letters/digits separated by hyphens or underscores, up to 80 characters. Creation now asks only for the rocket name and whether to start empty or upload an existing archive. The server generates the URL internally and adds numeric suffixes for duplicate names, including concurrent creation; existing explicit API slugs retain their prior validation/409 contract. The root rocket name and archive filename remain document data: importing a different archive or renaming its components does not rename the public URL or metadata title. Username changes, URL/title changes, account deletion and rocket deletion are not exposed in this increment.

## Authentication and editing

Reuse the already-pinned Better Auth 1.7.25, its Drizzle adapter and Drizzle 0.45.4 from the platform proof, without changing the proof. Self-service signup collects username, email and password; sign-in accepts username/password, and sign-out revokes the D1 session. The [username plugin](https://better-auth.com/docs/plugins/username) handles normalization and uniqueness; the library owns password hashing and HttpOnly/SameSite cookies, with Secure cookies on the configured HTTPS origin. Session cookie caching is disabled. Public directory/session summaries contain no email addresses. Email verification/recovery, password/account settings, administrators and per-rocket roles remain deferred; this is not the complete T05 account-management packet.

Only signup, username sign-in, get-session and sign-out library endpoints are routed. Same-origin checks protect account POSTs, rocket creation and socket upgrades, with the explicit configured auth origin. Metadata JSON bodies are bounded to 16 KiB. Visitors receive a read-only socket, can inspect/download archives, choose units and run supported simulations in their own browser. Mutation controls are disabled, and the server independently refuses anonymous commands, including forged username parameters.

On socket upgrade, the server derives the display username, session ID and user ID from the authenticated cookie. It replaces any supplied internal rocket header with the resolved D1 UUID. Socket attachments preserve those server-derived identities through hibernation. Every command rechecks the D1 session and rocket existence before applying it and again immediately before committing the resulting draft. Logout/expiry observed by the final check rejects and rolls back the edit; an operation already past that check may finish its DO transaction. There is no cross-store transaction between D1 session revocation and DO storage. Existing sockets remain public readers when their next write discovers revocation. The UI receives a read-only access message and requests sign-in before further edits.

All signed-in accounts may edit any public rocket, including Open/sample replacement. File New rocket navigates to the signed-in user's creation form, rather than clearing the currently viewed rocket. Existing atomic archive commands, whole-draft conflict refusal, durable acknowledgment, stale component draft retention and reconnect-without-replay rules remain as documented in the [coediting record](coediting-poc.md). The former `everyone` object's draft is not deleted or automatically assigned to an arbitrary first account; it is no longer routed by the new app. Export that earlier draft before upgrading if it is needed for an owned rocket.

## Run and deploy

`npm run build:app --prefix web` builds/typechecks the browser and server. `npm run preview:cloudflare --prefix web` applies migrations to Wrangler's local D1 emulator, supplies a process-only development auth secret and starts the local Worker on `http://127.0.0.1:8787`. No preview command writes to remote D1. An unset development secret is regenerated on restart, so sign in again; pass a stable `AUTH_SECRET` environment value to retain local session cookies across restarts. Plain Vite still supplies the earlier browser-local editor with no accounts/backend.

The tracked Wrangler config binds the real remote D1 database and declares `AUTH_SECRET` as required. Its `AUTH_BASE_URL` is the default loopback preview origin. Before a separately authorized deployment, set `OPENROCKET_ORIGIN` to the exact deployed HTTPS origin without a trailing slash and supply a stable, private `AUTH_SECRET` of at least 32 characters through the process environment. Keep that secret for subsequent deployments; rotating it invalidates signed cookies. Never use the tests' fake secret in production.

The existing `./deploy-cloudflare.sh --dry-run` remains a build-only command. The actual deployment path now uses `web/app/scripts/deploy-cloudflare.mjs`: it applies remote D1 migrations, overrides the auth origin, and uploads the secret with the same Worker deployment through stdin. It creates no secret file or secret command argument. A shell pipe is necessary because Wrangler reopens `/dev/stdin` and Node's direct child pipe is a socket on this host. The helper's own `--dry-run` skips remote migrations and upload. No deployment helper was run without `--dry-run` in this task. For a different Cloudflare account, create a separate D1 database and update the binding before deploying; do not point a second app at this account's database.

## Creation and upload follow-up

The subsequent November 20 request removes the URL-name field and path preview from the New rocket form, and adds **Start with → Upload existing rocket**. The file picker accepts `.ork`; selecting a file fills an empty name from its filename, while allowing a different display name. Empty creation sends name-only JSON. Upload creation sends the name and original file as multipart form data to the same authenticated, same-origin `POST /api/rockets` endpoint. There is no path choice or preview during creation. Shared URLs and existing directory links remain available after creation. See ADR-28.

The existing server codec validates uploads and retains opaque data and unchanged original bytes. The API bounds multipart bytes to the 4 MiB file limit plus 16 KiB form overhead, enforces the file limit separately, and checks the filename/name. It initializes a fresh Durable Object through a binding-only path and persists the accepted archive before inserting public D1 metadata. Thus an invalid upload cannot publish an empty rocket, and the first public visitor receives the uploaded document. On an ordinary metadata failure, the API requests cleanup of the unpublished staged object; the object refuses cleanup if metadata already exists. There is no cross-store crash transaction: a process failure before metadata publication may leave an unreachable staged object. General abandoned-object collection remains deferred. Existing rockets and the explicit in-editor Open workflow are unchanged. No database migration, remote resource modification, deployment or push is needed for this follow-up.
