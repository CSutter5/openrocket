# Tube motor-mount controls

The November 20, 2026 follow-up reports that tubes cannot be selected as motor mounts and supplies the desktop Motor tab as the reference. ADR-31 supersedes the earlier link-only Motor tab and the mount-creation deferral in ADR-22/25 for body and inner tubes. Rocket name/password settings from the same request are recorded separately in [account settings](account-settings.md).

## Editing contract

BodyTube and InnerTube dialogs now expose This component is a motor mount, signed motor overhang with independent length units/slider, the five native ignition events, and a non-negative ignition delay with independent time units. Mount-dependent controls disable while the checkbox is off. Cancel/Escape retain accepted bytes; changing units or toggling off/back on without a value change is an exact no-op. Apply and open Motors & Configuration first saves all tab/name changes atomically, then opens the existing workspace, so a newly enabled tube is available to catalog selection immediately.

The new typed mount settings are part of the existing hash-guarded `componentProperties` command. Both the browser document Worker and trusted Cloudflare Durable Object use the same finite-number/event/type validation and archive transformation. Only body/inner tubes can receive a mount; no arbitrary nested XML editing is exposed. Mount settings, scalar properties and optional component name publish as one candidate after export/reimport and view construction. Invalid or stale input retains the accepted archive and other dialog drafts. Duplicate mount/default definitions refuse mount editing rather than selecting an arbitrary value.

Enabling creates the native `<motormount>` container with ignition defaults and overhang. Updating a mount edits only the known defaults while preserving assignments, explicit per-flight ignition, unknown data and attachment bytes. New default fields are inserted before motor instances, as required by the native loader's inheritance order. Older files without explicit per-flight ignition receive explicit copies of their old inherited values when defaults change: native motor instances copy defaults during loading, and changing the defaults does not alter those existing instances. This is verified against the actual native setters and serialization, rather than inferred from XML shape alone.

Disabling removes that tube's mount container and assignments, matching native save behavior, while retaining root flight configurations, simulations and motor assets. The dialog explains this consequence before save. Enabling/disabling and overhang changes mark affected historical results outdated while retaining stored series. Default-only ignition changes preserve existing per-flight settings/results; new assignments inherit the new defaults. Existing unsupported imported geometry/flight profiles continue to refuse simulation explicitly. No physics algorithm, engine adaptation, library dependency, database schema, cloud service or production JVM is added.
