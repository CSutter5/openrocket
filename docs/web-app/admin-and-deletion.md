# Creation cards, owner deletion and administrator tools

The November 20, 2026 follow-up requests separate scratch/upload blocks, confirmed owner deletion, and a private administrator panel. The user explicitly chose a new `admin` account with temporary password `admin`, to be changed at first login. This is a bounded extension of T05 and ADR-27/28, recorded in ADR-29. Public reading and editing by every signed-in account remain unchanged after account setup.

## Creation and deletion

The library has two independent forms: Start from scratch and Upload a rocket. The second accepts a selected or dropped `.ork` file and an editable name; selection fills an empty name from the filename. There is no source dropdown, path field or path preview. The cards stack on narrow screens. The existing validated-upload publication boundary and exact-byte/asset preservation remain in effect.

Owners can delete their rockets from the directory or editor header. The administrator can delete any rocket. All destructive UI actions open a native modal with an explicit are-you-sure message, Cancel focused first, and a permanent-deletion explanation. Server checks independently require a live owner/admin session and the configured same origin. Deletion also requires the immutable `rocketId` query parameter, preventing an old confirmation from deleting a replacement at a reused public URL.

The Durable Object serializes deletion with document commands, independently rechecks authority, marks D1 metadata deleted, notifies/closes connected sockets, deletes its stored archive and identity, then removes metadata. Deleted entries immediately disappear from public reads and refuse socket upgrades/writes. The browser enters a terminal deleted state; reconnect requests retain the UUID and refuse a replacement at the same URL. There is no distributed D1/DO transaction. A failed cleanup retains hidden tombstoned metadata for retry; the admin directory includes pending deletion entries. A successful deletion cannot be undone; no revision storage is added.

## Administrator bootstrap and access

Migration `0002_admin_and_deletion.sql` adds the singleton `app_admin` relationship, mandatory-password flag and credential counter, the user-deletion marker, and rocket tombstones. It inserts the reserved `admin` user and a credential hash generated with the pinned Better Auth password helper for the requested temporary password. D1 migration tracking applies this once; subsequent previews/deployments never reseed or reset an existing password. A conflicting bootstrap username/email fails the migration rather than granting an existing user administrator rights. Public signup refuses reserved names, and client role fields cannot grant privileges.

Sign in from the home page with username `admin` and password `admin`. The first screen requires the current password and a new password of at least eight characters, entered twice. The server refuses document creation, shared writes and all management data/actions until that change succeeds. Better Auth verifies/hashes the replacement and issues a new session; a D1 batch then revokes every other admin session, clears the mandatory-change flag and increments the credential counter. Admin sign-ins compare that counter before/after authentication and revoke sessions that raced with a password change. Cookie session caching remains disabled and authorization queries current D1 state.

After setup, only that singleton account receives the Admin panel link and access to `/admin/` or `/api/admin/*`. Both HTML and API access are guarded on the server. The panel lists users and all rocket metadata, deletes users with all their owned rockets, deletes individual rockets, and revokes ordinary users' sessions. The sole administrator cannot delete itself or revoke its own sessions through these tools, and there is no public role-assignment endpoint. Its library uses `/?owner=admin` because `/admin/` is reserved for management; individual admin-owned rocket paths remain `/admin/<slug>/`.

User deletion first marks the account unavailable and revokes sessions in D1, then removes each owned rocket through its Durable Object, and finally deletes the user and cascading credentials/sessions. Creation uses a conditional D1 insert against the active account, closing the create/delete race. Shared writes recheck both the editor and rocket owner's availability. Partial deletion leaves a marked user visible to the administrator for retry and returns an error rather than reporting completion. Session revocation is enforced at the next write and at the final persistence check; an edit already past that check may complete. This retains the existing cross-store revocation limit.

No email delivery/recovery, suspension, general role management, ownership transfer, per-document permissions, audit log or version history is added. If the administrator loses its password, operator recovery remains manual Cloudflare administration; the app does not expose a reset-to-default endpoint. No engine, reducer or numerical code changes are included.
