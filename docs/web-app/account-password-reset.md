# Administrator-issued temporary passwords

The November 20, 2026 request authorizes an administrator to set a user's temporary password and require its replacement. The user explicitly chose to keep rockets unlimited: there is no per-account rocket-count quota or quota setting. Creation remains in `web/app/server/index.ts`; archive byte limits are separate from the number of rockets.

## Use and data migration

After administrator setup, open **Admin panel → Users → Reset password**, enter and confirm a temporary password of 8–128 characters, and choose **Set temporary password**. The administrator gives that password to the user; the app sends no email and never returns/stores plaintext passwords. The panel labels accounts awaiting a password change. The sole administrator continues to use Account settings for its own password; these tools cannot reset or delete that protected account.

Migration `web/app/migrations/0005_temporary_passwords.sql` adds `user.must_change_password` with a false default for existing and new ordinary users. It copies the existing administrator's setup flag, preserving both completed and unfinished setup without replacing credentials or sessions. The user column becomes authoritative; normal administrator password changes also maintain the legacy `app_admin` flag/counter. Use the existing local preview migration workflow for local development. A future authorized deployment must apply this migration before serving the updated Worker, using the existing deployment helper. No remote migration or deployment was performed for this request.

Every old session is revoked when the administrator sets a temporary password. After signing in with it, the user sees the required change screen, including when visiting a private rocket URL. They enter the temporary password as Current password and choose a different replacement twice. A successful change returns ordinary users to the library and the bootstrap administrator to its panel. Pending changes block creation, rename, deletion, sharing management, preferences and shared writes through the existing server checks. Public viewing remains available under the existing sharing policy. Existing sockets must pass live D1 session/access checks before writing and before persistence; a document operation already past its final access check may finish, retaining the documented D1/DO boundary.

## Architecture decision: atomic account recovery

This supersedes ADR-30's password-write orchestration while retaining the pinned Better Auth account/session implementation. Use the configured Better Auth context's [password hashing and verification helpers](https://better-auth.com/docs/concepts/hooks), including its configured length policy, for both self-service changes and administrator resets. No custom hashing, password-reset token transport, email service, new dependency or general role/impersonation endpoint is introduced. Indexed upstream issue/PR searches found no matching web account recovery implementation; that discovery is not exhaustive and no maintainers were contacted.

Write the new credential hash, required-change flag and session revocation in one atomic D1 batch. A conditional credential update compares the previously read hash and rechecks the initiating session; administrator resets additionally recheck the protected administrator relationship and target availability. Later statements depend on the freshly generated replacement hash so a failed conditional update cannot clear a flag or revoke sessions. A concurrent credential change or revocation returns a conflict rather than overwriting a reset. Existing before/after credential checks continue to fence racing sign-ins.

Self-service changes verify the current password and reject a replacement that verifies against the same hash, covering Better Auth's Unicode normalization. They retain the already-authenticated current session and revoke every other session in that same batch. The preceding implementation called Better Auth's change-password endpoint, then separately cleared the administrator flag. Its writes cannot be made atomic with the application's general required-change flag, and its read/hash/write sequence can overwrite a concurrent administrator reset when the adapter has no transaction support. Reusing library password helpers while controlling the D1 batch closes that gap. Enabling the broader admin plugin would introduce a second privilege representation and unrelated endpoints; it is unnecessary for this bounded recovery action.
