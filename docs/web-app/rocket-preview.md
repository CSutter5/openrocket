# Rocket preview statistics and internal components

The November 20, 2026 follow-up requests the desktop preview arrangement: physical properties at the upper left, stability and CG/CP at the upper right, selected-configuration flight statistics at the lower left, and visible internal components. This is a bounded extension of the existing axial SVG preview. No deployment, remote migration, new dependency or runtime service is included.

## Values and drawing

The existing native `EditorStability` calculation now returns configuration length, maximum core shell diameter, structure mass, launch mass, caliber reference and aerodynamic length alongside CG/CP. These use the desktop `RocketInfoContextHelper` definitions: `FlightConfiguration.getLength()`, maximum core symmetric fore/aft diameter, `MassCalculator.calculateStructure` and `calculateLaunch`. Stability is CP minus launch CG, evaluated with the existing worst-angle Barrowman CP at Mach 0.3, zero AOA and roll rate. Calibers use native `CaliberUnit.calculateCaliber`; percent uses aerodynamic length. Neither uses an arbitrary rocket reference area or simulation altitude. Nonfinite native values and zero-force CP remain unavailable.

The same reconstructed native model exports internal tube/ring/coupler/block/bulkhead rectangles, rounded packed mass/recovery/cord shapes, shell shoulders and selected motors. Dimensions and instance positions come from native getters. Inner-tube radial positions are already included in native instance locations; mass-object offsets are applied separately, as in desktop side shapes. Tube inner outlines use the desktop 1.2 mm wall threshold. Packs have simple recovery/cord symbols rather than every desktop decorative icon. Outlines are dashed, motors solid, and accessible names identify their components. Mouse/keyboard selection uses existing component IDs and dialogs. Native UUIDs are matched back to the archive's original ID spelling, including uppercase IDs. Internal strokes remain selectable without covering the entire exterior hit area. CG and CP retain differently shaped blue/orange markers and text labels.

The existing sampled native exterior polygons remain intact. Fit includes internal bounds and centers the rocket horizontally when height limits its scale. Header/footer sections scroll within bounded heights on small viewports. The existing single direct axial stage, supported component fields, resolved motor curves and archive analysis limits still apply. Pods, boosters, clusters, arbitrary extensions and unsupported graphs are not guessed. Inspection/export and the exterior drawing retain their prior refusal behavior; omitted shapes and unavailable analyses remain identified. This does not establish general G1/G5 or full desktop drawing parity.

Personal unit defaults now apply to mass, flight distance, velocity, acceleration and primary/secondary stability. Rocket dimensions and CG/CP use the current drawing length unit. The secondary visibility flag is honored and duplicate primary/secondary units are suppressed. Unit choices remain presentation state and never change engine globals, shared XML or simulation inputs.

## Configuration and result freshness

Like desktop `findCurrentConfigurationSimulation`, the preview uses the first saved simulation matching the selected motor configuration. It never borrows another configuration's result or starts a run automatically. Apogee and velocity come from the existing four-element summary. Maximum acceleration is a separate field from native `FlightData.getMaxAcceleration()`, including its desktop flight-phase semantics, or the archived `flightdata` attribute. Missing values display Unavailable.

Completed browser results are held in the app's existing session lifetime and supplied to both simulation table and preview. A result must match simulation and configuration IDs; archive and identity hashes distinguish Completed from Outdated result. Archived values are labeled Stored result or Outdated result; absent runs are labeled Not run. The preview does not imply that imported historical results have independently verified provenance. Results remain browser-local under the existing contract.

The regression check found that a name-only component-dialog save retained the old archive hash. That path now refreshes its identity hash after renaming, matching the existing direct rename command. This necessary correction makes dirty state, concurrency preconditions and displayed result freshness reflect the accepted bytes.

## Ruler alignment follow-up

The screenshot-reported ruler error came from combining a fixed screen-space tick pattern with labels calculated from the centered rocket. Ticks and labels now share the rocket's physical coordinate transform, with zero at its origin and the ruler spanning the drawing bounds. Major intervals use regular 1/2/5 decade steps in the selected unit; minor ticks subdivide those same intervals. Labels are centered on their major ticks. Resizing, zooming and metre/inch changes retain alignment with component locations. No engine, archive, account or simulation behavior changes.

The drawing regression checks the ruler against the independently known 0.52 m sample length and 0.0254 m/in conversion, including origin/end alignment and actual screen positions at four viewport sizes and two zoom levels. The production build (`npm run build:app --prefix web`) and the `drawing.mjs` and `layout.mjs` regressions passed in Chromium 149.0.7827.55, using the same native classpath/browser environment documented below and a process-owned Vite preview on port 4178. The drawing regression covers 16 ruler cases; the layout regression covers all seven viewport sizes. A read-only browser check of the existing user rocket also confirmed zero/nose alignment in inches and exact unchanged source archive bytes. The wide sample and user-rocket screenshots under `web/app/build/gp/ruler-*.png` were inspected. Node syntax and diff-whitespace checks passed. Initial test attempts used inconsistent Playwright/SVG bounding boxes and font glyph bounds; the passing regression measures actual SVG client coordinates and text anchors instead. No engine rebuild or full numerical/aggregate acceptance rerun was needed for this presentation-only correction.
