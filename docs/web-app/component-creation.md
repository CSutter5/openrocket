# Component creation, drawing stability and units

The November 19, 2026 user follow-up authorizes component creation using menus close to desktop OpenRocket, CG/CP locations on the drawing, and selectable simulation units. This supersedes the component-creation deferrals in the earlier desktop workspace record. ADR-23 records the bounded extension; broader feature parity and G1/G5 remain held.

The existing palette retains desktop groups, labels and icons. All 21 component types can be created. Compatibility comes from the pinned native `isCompatible` methods, exported alongside native saver fragments at build time by `ComponentDefaultsExporter`. Body components can be inserted after a selected body component or appended to its assembly. Stages append to the rocket, including an active-stage reference in each existing configuration. Other components append to the selected compatible parent. New components get fresh UUIDs, become selected, and open the existing component editor. File → New creates a rocket with an empty axial stage. Existing limits on editable properties remain: names and supported explicit BodyTube dimensions, rather than complete desktop configuration dialogs. Automatic tube dimensions and other component properties remain read-only.

The browser generates no component XML from guessed defaults. It inserts native fragments, marks stored results outdated, exports and reimports the candidate with the existing simulation identity sidecar, and publishes only after view construction succeeds. Existing component XML, opaque fields, assets and stored series remain preserved. Creation is limited to editable archives and 64 components. Insertion captures the original component and archive hash so changing selection or replacing the file cannot silently redirect an insertion. Native tube-fin construction leaves thickness undefined (`NaN`); the web initialization explicitly uses the native BodyTube default wall thickness so newly created tube fins have a finite wall. This is the one deliberate default adjustment, covered by the desktop setter/serialization oracle.

The drawing shows labeled CG and CP symbols with different shapes and colorblind-safe colors. Locations are axial coordinates from the rocket origin. CG uses native `MassCalculator.calculateLaunch`, including overrides, internals and selected motors. CP uses native Barrowman `getWorstCP` at Mach 0.3, zero angle of attack and zero roll rate, matching the desktop design-view conditions. A zero normal-force contribution produces no CP marker; empty designs produce no CG marker. Static reconstruction accepts the established imported components plus elliptical fins, tube fins, launch lugs, rail buttons, streamers, centering rings, couplers and engine blocks. Optional geometry uses native constructor defaults; group/shear metadata does not affect static mass or CP. Rail-button construction reads bundled materials through the immutable preferences shim; user-material mutation throws. Unsupported fields/graphs, freeform fins, unresolved motors and multistage/pod designs show an unavailable reason rather than partial stability values. Creation of these components is still supported. The established exterior renderer still lists shapes it omits; the static calculation includes supported omitted internals and exterior types. Native conical/ellipsoidal profiles need no stored shape parameter, so their drawing projection now accepts that omission.

The simulation toolbar and graph expose units directly. Millimeters, centimeters, meters, kilometers, inches, feet, yards and miles share exact SI conversion factors with the drawing, ruler and dimension controls. Velocity follows the selected length unit per second; time remains seconds. Kilometers/miles retain six decimal places in result tables. Changing units does not edit the archive, rerun a simulation or change result provenance.

## Verification and handoff

`test/components.mjs` drives the real browser palette, downloads each created component, and compares complete native serialization and native save/reload through `ComponentDesktopProof`. It also checks compatible/disabled parents, insertion/cancellation, File New and reopen, native CG/CP for supported created types and two motor configurations, all eight result/plot units, and byte-identical unit-only downloads. The normal acceptance runner includes it after fixture generation. Reports, archives and screenshots remain in ignored `web/app/build/gp/`.

Build with `node web/engine-adapter/scripts/build.mjs`, then `npm run build:app --prefix web`. The app prebuild/predev exports component defaults using the same native runtime classpath already required for motor generation. With the documented test classpath, `npm run test:app --prefix web` runs the existing browser/native regressions and this extension. No new dependencies, changes to core Java sources, hosted compute, deployment or Git push are needed.

The upstream duplicate-work search was partial: a web search for OpenRocket web component creation did not establish an existing matching issue or PR. This is the explicitly requested local application extension, not an upstream parity claim or authorization to contact maintainers.
