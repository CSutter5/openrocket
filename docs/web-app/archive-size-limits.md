# Large saved-flight archives

The November 20, 2026 report describes “Expanded archive limit” when uploading a third rocket. There is no rocket-count quota. The supplied `L00k 50k 3in to 2in.ork` is 3,337,533 uploaded bytes, containing 10,631,706 XML bytes and 10,664,387 expanded bytes overall. Its XML contains eight saved simulations, 16,786 flight datapoints, 18,260 elements and maximum depth 11. The prior 8 MiB per-entry check rejected `rocket.ork` before decompression, despite the archive fitting the existing 4 MiB upload and 16 MiB total-expanded budgets. The failure was reproduced locally before editing.

## Decision and behavior

ADR-37 permits an individual ZIP/GZIP entry to use the existing 16 MiB archive budget. This supports the reported saved-flight data without discarding simulations or increasing the total-expanded or upload budgets. The XML element/depth, entry-count, CRC, path, declared-size and streaming-inflation checks remain in effect. Plain XML still has to fit the 4 MiB upload budget. No account quota, schema migration, engine algorithm or desktop serializer changes are involved.

ZIP entry-size failures now identify the entry, its declared expanded byte count and the per-entry limit. Aggregate failures identify the running expanded total and the per-upload total limit; ZIP64 compressed-size failures are distinguished as unsupported sizes. Existing error codes are retained. These messages propagate through the actual upload API and library error display, and an unsuccessful upload creates no rocket metadata.

Rejecting all files with saved XML above 8 MiB unnecessarily restricts legitimate files already within the total budget. Removing stored flight data would change the user's file. Raising every bound or adding per-user configuration is unnecessary for this report. This change does not establish hosted CPU/memory headroom for every allowed input; the local runtime evidence below covers the supplied archive and independent fixtures.
