# Rocket sharing permissions

The November 20, 2026 follow-up authorizes Public/Restricted viewing, selected Viewer/Editor accounts, live revocation and downgrades, ownership transfer and download permissions (ADR-32). This replaces ADR-27's blanket signed-in editing. It does not add history, groups, unlisted links, comments, expiring grants or email invitations, or pass the broader G2/G3 gates.

## User contract

New scratch and uploaded rockets are Restricted. Owners use Share in the directory or editor to change visibility, add existing accounts by username, change Viewer/Editor roles and download flags, or remove a user. Public visibility grants anonymous viewing, including directory discovery, but never editing. A removed user still has public viewing access when the rocket is Public. The signed-in directory includes public, owned and explicitly shared rockets; owner pages filter by current owner. Restricted metadata and archive/socket access return 404 to unrelated accounts and visitors.

Viewers inspect designs and run simulations locally. Editors can change components/settings and replace the shared archive through Open. Owners and the administrator manage sharing, rename and delete; the administrator retains full viewing, editing and download access after mandatory account setup. Only the current owner can transfer ownership. The recipient must be an existing available account. The confirmation explains that the former owner becomes an Editor with downloads allowed and that the share URL stays the same. Other collaborators and archive data remain unchanged. The new owner can subsequently revoke the former owner's access.

Public downloads have a separate checkbox. Each selected user's explicit download flag overrides the public default independently of Viewer/Editor role. Owners and the administrator always have downloads. Shared export uses a checked server endpoint, and denied export controls are disabled immediately when sharing changes. This controls the application's .ork export workflow: authorized viewers already receive complete archives for browser rendering and local simulation. It cannot prevent extracting browser data, retrieving visible information, or retaining previously downloaded copies. The Share dialog states this limitation.

## Storage and concurrency

Migration `0003_sharing.sql` rebuilds only the rocket metadata table, preserving immutable IDs, names, slugs, timestamps and deletion tombstones. Existing rockets retain Public visibility and public downloads. No members are generated: other signed-in accounts lose implicit editing and require an explicit Editor grant. New rows default to Restricted with public downloads disabled. Membership roles/download flags are constrained and cascade with rocket/account deletion.

An immutable `route_username` separates the share URL from current ownership. Transfer changes the owner without changing UUID, share URL or archive bytes, even if the recipient already owns a rocket with the same slug. Creation reserves existing route/slug pairs, including rockets previously transferred away. Current ownership controls owned lists and account deletion; deleting a former owner must not delete the transferred rocket. The directory, renaming and deletion clients use the stored route rather than the current owner's username.

D1 stores visibility, grants and a sharing version. The rocket's Durable Object serializes sharing changes, transfers, downloads, socket joins and document commands through the existing queue. Sharing writes require same origin, a live owner/admin session, matching immutable rocket ID and expected sharing version. Transfers additionally require the current owner. Atomic D1 batches change visibility/grants/ownership and increment the version. An owner-availability trigger fences transfer against an administrator concurrently marking the recipient deleted. Stale sharing forms must reopen before retrying.

Sockets retain server-derived session/account identities across hibernation. Sharing changes recheck every connected socket: downgrades update edit/export controls, removed private readers receive a terminal revocation message and close, and retained readers receive current owner/visibility metadata. Revocation clears the visible editor. Every command rechecks editing authority before application and immediately before persistence. Every state broadcast, including rejected-command snapshots, rechecks each recipient's live session and read access; access-check failures close the connection. Thus no later archive update goes to a revoked private reader. The queue orders edits and ACL changes: an edit queued before revocation may finish first; an edit after revocation is denied.

Session revocation/account deletion and room operations remain separate stores, without a distributed transaction. They use live checks at the documented command commit and broadcast boundaries. Passive session expiry does not erase data previously received. Hosted hibernation, deployment upgrade behavior, load and broader production recovery remain unverified.
